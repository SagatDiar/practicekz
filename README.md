# PracticeKZ — этапы 1–8: каркас, авторизация, заявки, списки, кабинеты, уведомления, статистика, тесты, реестры РК и проверка при входе

Стек: Node.js 20 + Express 5 + Prisma + PostgreSQL, React 18 + Vite + TypeScript.

## Запуск через Docker (одной командой)
```bash
cp .env.example .env
docker compose up --build
# во втором терминале, когда api запущен:
docker compose exec api npm run seed
```
После `seed` в базе уже есть реестр ВУЗов РК (этап 8). Реальный реестр юрлиц загружается отдельно — см. «Этап 8».
Веб: http://localhost:5173 · API: http://localhost:4000/api/health

## Что готово на этапе 1
- Схема Prisma для всех сущностей (User, профили, Practice, Application, DiaryEntry, ExtraEducation, File, Notification, Reference) с индексами.
- Seed: справочники (22 города, 8 факультетов, 24 специальности), 2 университета, 3 студента, 5 компаний, 10 практик, 5 заявок (PENDING, INVITED, REJECTED, SIGNING, COMPLETED с дневником и отчётом).
- Авторизация: bcrypt (cost 10), JWT в httpOnly cookie (access 15 мин + refresh 7 дней), автообновление на клиенте, rate limit на вход/регистрацию, проверка Origin, helmet, CORS только для фронтенда, `requireRole`.
- API: `/api/auth` (register, login, refresh, logout, me, me/password), `/api/reference` (cities, faculties, specialties, universities).
- Веб: вход, регистрация студента/компании, защита маршрутов по ролям (чужая роль → редирект в свой раздел), выход.

## Допущения
- bcryptjs вместо bcrypt: тот же алгоритм, но без нативной сборки в Docker.
- Университеты не регистрируются, только через seed.
- `docker compose` использует `prisma db push`; для продакшена создайте миграции: `npm run migrate`.
- Seed очищает все таблицы перед заполнением.
- Пакеты в этой среде не устанавливались (нет сети), поэтому запуск не проверялся; первый `npm install` подтянет зависимости.

## Этап 2: заявки, ЭЦП, дневник, отчёт

Проверка всего цикла на живом API (после свежего `seed`):
```bash
docker compose exec api npm run smoke     # или локально: cd server && npm run smoke
```
Скрипт проходит цепочку `заявка → приглашение → одобрение → 3 подписи → ACTIVE → дневник → отчёт → завершение → подтверждение` и проверяет запреты (403 / 404 / 409).

### Новые эндпоинты
| Метод и путь | Кто | Действие |
|---|---|---|
| `GET /api/practices` (`page`, `limit`, `q`, `mine`) | все | список; у студента флаг `applied`, у компании по умолчанию только свои |
| `GET /api/practices/:id` | все | карточка практики |
| `POST/PATCH/DELETE /api/practices[/:id]` | компания-владелец | создание, правка, удаление (409, если есть заявки) |
| `GET /api/applications`, `GET /api/applications/:id` | по роли | только свои заявки; в деталях дневник, отчёт, подписи, прогресс |
| `POST /api/applications` | студент | подача заявки |
| `POST /api/applications/:id/invite`, `approve`, `reject` | компания | решения по заявке |
| `POST /api/applications/:id/sign` | студент, компания, университет | каждый подписывает только за себя |
| `POST /api/applications/:id/request-finish` | студент | «Практика окончена» |
| `POST /api/applications/:id/confirm-finish` | компания | подтверждение завершения |
| `POST /api/applications/:id/diary`, `PUT /api/applications/:id/report` | студент | дневник и отчёт (после начала практики) |

### Как устроен автомат статусов
- Каждый переход — один `updateMany` с условием на статус и владельца, внутри транзакции: параллельные запросы не ломают состояние.
- Ошибки: 404 — заявки нет или она вам не видна; 403 — чужая заявка или роль; 409 — действие недопустимо в текущем статусе.
- Уведомления пишутся в таблицу `Notification` в той же транзакции (все события из промпта). Рассылка через Socket.IO и интерфейс — этап 5.
- Прогресс: `totalDays = durationMonths·30`; старт — `startDate`, иначе первая запись дневника, иначе дата заявки; `COMPLETED` = 100%.

### Допущения этапа 2
- Дата записи в дневнике не может быть больше чем на сутки в будущем.
- Практику с заявками удалить нельзя (409), чтобы не потерять историю.
- Тесты Vitest/Supertest — этап 7; смоук-скрипт их пока заменяет.
- Код проверен только на синтаксис (в моей среде нет сети для `npm install`), реальный прогон — за вами.

## Этап 3: списки, фильтры, сортировка, пагинация, CSV

### Единый движок списков (`server/src/utils/listEngine.ts`)
Каждый список описывается конфигом (`server/src/lists/*.ts`): базовое условие видимости по роли, фильтры, поиск, сортировки. Движок даёт три маршрута:

| Путь | Что возвращает |
|---|---|
| `GET /` | `{ items, total, page, pages, limit }` |
| `GET /facets` | счётчики значений для панели фильтров (`?facets=status&facets=city` — только нужные группы) |
| `GET /export.csv` | CSV с теми же фильтрами и сортировкой (UTF-8 BOM, разделитель `;`, без столбца «Действия», защита от формул) |

Параметры: `q`, `page`, `limit` (10/25/50/100), `sort=поле:asc|desc`, фильтры повторяющимися параметрами (`status=A&status=B` → `IN (...)`).
Счётчики группы считаются **без её собственного фильтра**, но с остальными фильтрами и поиском — можно добавить ещё значения в той же группе.

| Список | Эндпоинт | Роль | Фильтры |
|---|---|---|---|
| Найти практику / Мои предложения | `/api/practices` | студент / компания (только свои) | city, format, direction, duration, company, `hideApplied=1` |
| Мои заявки / Заявки студентов / Практика | `/api/applications` | студент / компания / университет (каждый только своё) | status, company, practice, duration, city, studentCity, specialty, faculty, course, university, `dateFrom`, `dateTo` |
| Студенты | `/api/students` | университет (только свои студенты) | faculty, specialty, course, city, company (или `none` = «Без практики»), status |
| Компании | `/api/companies` | университет | city, industry |

### Интерфейс (`web/src/components/filters`, `web/src/hooks/useListQuery.ts`)
- `SearchBar` — поиск (debounce 300 мс) и одна кнопка «Фильтр» с бейджем числа активных групп.
- `FilterDrawer` — панель справа (на мобильных нижний лист): сворачиваемые группы, мультивыбор, мини-поиск и «Показать все» в длинных списках, счётчики значений, диапазон дат, переключатель, «Применить» и «Сбросить всё».
- `FilterChips` — чипы выбранных значений с удалением по одному.
- `useListQuery` — всё состояние (фильтры, поиск, страница, сортировка) хранится в URL: обновление страницы и ссылка сохраняют список.
- `ListShell` собирает всё вместе: загрузка, пустой результат («Ничего не найдено. Попробуйте изменить фильтры» + «Сбросить»), пагинация, CSV. `SortHeader` — сортировка по клику на столбец (▲/▼).
- Конфиги групп фильтров для всех семи списков — в `filterConfigs.ts`.

Работающие страницы этапа 3: `/student/practices`, `/student/applications`, `/company/practices`, `/company/applications`, `/university/practice`. Списки студентов и компаний университета готовы на сервере, страницы для них — на этапе 4.

### Допущения этапа 3
- Счётчики фильтров по связанным полям считаются по строкам, а не через `GROUP BY` (Prisma не группирует по связям): на каждую группу один лёгкий запрос по одному столбцу, лимит 50 000 строк. На 5000+ заявок это быстро; при росте на порядок счётчики стоит перенести в SQL-представление.
- «Текущая» практика студента в списке университета: приоритет ACTIVE → FINISH_REQUESTED → SIGNING → COMPLETED → INVITED → PENDING; отклонённые заявки не учитываются («Без практики» = нет неотклонённых заявок).
- Курс — мультивыбор по значениям, а не ползунок диапазона.
- Действия в таблицах (подписать, пригласить и т.д.) и модальные окна — этап 4.
- Код проверен только на синтаксис (нет сети для `npm install`); запустите `npm run smoke` после `seed`.

## Этап 4: кабинеты, модальные окна, профиль, файлы

### Интерфейс
- **Каркас:** тёмный sidebar слева (на телефоне выезжает поверх) и topbar с именем и аватаром. Пункты меню по ролям — см. `components/PageFrame.tsx`.
- **Главные страницы** (`DashboardPage`, данные с `GET /api/dashboard`):
  - студент: 4 счётчика, «Моя практика» с прогрессом и действиями, «Рекомендуем» (сначала практики в его городе);
  - компания: счётчики и 5 последних заявок с кнопками действий;
  - университет: счётчики и список документов, ждущих подписи университета.
- **Действия по заявке** (`ApplicationActions`) зависят от роли и статуса: пригласить, одобрить, отклонить, подписать ЭЦП, «Практика окончена», подтвердить завершение, дневник. После каждого действия обновляются все списки и сводки.
- **Модальные окна:** практика (с кнопкой «Подать заявку»), подписание ЭЦП в стиле eGov, дневник и отчёт (студент пишет, остальные читают), профиль студента с сертификатами.
- **Университет:** страница «Студенты и практика» с вкладками «Студенты», «Компании», «Практика»; при смене вкладки фильтры сбрасываются.
- **Профиль:** редактирование данных, смена фото или логотипа, студент ещё управляет сертификатами и достижениями.
- **Компания:** форма «Добавить практику» с валидацией (срок 1–6 мес.).

### Файлы и безопасность
- Загрузка: `multer` в память, лимит 5 МБ. Фото: только изображения, обрезаются до 256×256 JPEG через `sharp`. Сертификаты: PDF, JPG, PNG, WEBP; проверяются MIME, расширение и содержимое (сигнатура `%PDF-` или декодирование изображения).
- На диске файл хранится под случайным именем (`uploads/<uuid>.<ext>`), исходное имя — только в БД.
- `GET /api/files/:id`: аватары видны авторизованным; сертификат — владельцу, его университету и компании, получившей от студента заявку. Остальным 403.
- Удаление записи удаляет и файл; замена файла удаляет старый.
- `GET /api/students/:id`: сам студент, его университет или компания с заявкой от него.

### Новые эндпоинты
`GET/PATCH /api/profile`, `POST /api/profile/photo`, `GET/POST /api/profile/extra`, `POST /api/profile/extra/:id/file`, `DELETE /api/profile/extra/:id`, `GET /api/files/:id`, `GET /api/students/:id`, `GET /api/dashboard`.

### Допущения этапа 4
- Загруженные файлы в Docker лежат в томе `uploads`; антивирусной проверки нет.
- Университет не может менять свою роль или создаваться через UI.
- Уведомления (колокольчик, toast в реальном времени) — этап 5; пока они только пишутся в БД.
- Статистика и диаграммы — готовы на этапе 6 (см. ниже).
- После `npm install` в `server` будет собран `sharp` (нативный модуль); в Docker-образе это происходит автоматически.
- Код проверен только на синтаксис (нет сети для `npm install`); `npm run smoke` после `seed` проверит сервер.

## Этап 5: уведомления в реальном времени (Socket.IO)

### Как это работает
- Сервер и сокеты живут на одном порту (`server/src/server.ts`, `server/src/realtime.ts`). Сокет авторизуется тем же httpOnly-cookie с access-токеном; без него соединение отклоняется. Каждый пользователь сидит в своей комнате `user:<id>`, чужие события получить нельзя.
- Уведомление создаётся в той же транзакции, что и смена статуса (`notify`), а рассылка по сокетам идёт **только после успешного коммита** (`runTx` в `services/notify.ts`). Если действие отклонено (409, 403) или транзакция откатилась, события не будет.
- События покрывают все переходы заявки: новая заявка (компании и университету), приглашение, одобрение, отклонение, подписи ЭЦП, начало практики, запрос и подтверждение завершения, запись в дневнике, отчёт.

### API
| Метод и путь | Действие |
|---|---|
| `GET /api/notifications?page&limit&unread=1` | свои уведомления, новые сверху; в ответе `unread` и пагинация |
| `GET /api/notifications/unread-count` | число непрочитанных |
| `PATCH /api/notifications/:id/read` | отметить прочитанным (чужое → 403) |
| `POST /api/notifications/read-all` | прочитать все |

Событие сокета: `notification` с полями `id, type, text, applicationId, read, createdAt`.

### Интерфейс
- Колокольчик в topbar с красным счётчиком, выпадающий список (20 последних), «Прочитать все», клик по уведомлению отмечает его прочитанным и открывает раздел заявок.
- При новом событии: всплывающее сообщение, счётчик растёт сразу, а таблицы, главные страницы и дневник обновляются сами, без перезагрузки.
- После обрыва связи данные перечитываются; запасной опрос раз в 2 минуты на случай недоступности сокета.
- Vite проксирует `/socket.io` с поддержкой WebSocket (`vite.config.ts`).

### Допущения этапа 5
- Access-токен живёт 15 минут, но уже открытое соединение им не ограничивается; при перезагрузке страницы сокет подключается заново с актуальным cookie.
- Одно соединение на вкладку, масштабирование на несколько серверов (Redis adapter) не делалось.
- Отдельной страницы «Все уведомления» нет: хватает выпадающего списка на 20 записей.
- Смоук-скрипт теперь подключает реальные сокеты (нужен `socket.io-client`, он в devDependencies).
- Код проверен только на синтаксис (нет сети для `npm install`).

## Этап 6: статистика (вкладки, горизонтальные диаграммы, кликабельная круговая)

### Как устроено
- Страница «Статистика» есть у всех трёх ролей (`/student/stats`, `/company/stats`, `/university/stats`). Вверху вкладки; **в DOM только выбранная**, данные грузятся по требованию отдельным запросом. Вкладка хранится в URL (`?tab=faculties`), как и фильтры.
- **Круговая диаграмма** — отдельный блок: клик по сегменту (или по строке легенды) выдвигает его и показывает под диаграммой «**2** из 5 заявок (**40%**) — Практика идёт»; повторный клик снимает выделение. В центре — общее число.
- **Столбчатые диаграммы — только горизонтальные** (`indexAxis: "y"`), каждая на всю ширину, строки по убыванию значения, высота = `строки × 40 + 70` px. Пустой результат: «Данных пока нет».
- На каждой вкладке справа вверху кнопка **«Фильтр»** (та же панель, чипы и мультивыбор, что в списках), **CSV** (с теми же фильтрами, считает сервер) и **PNG** (для вкладок с диаграммой).
- Графики обновляются сами при новых уведомлениях (`stats` входит в список обновляемых запросов).
- Chart.js вынесен в отдельный файл и загружается только при заходе в статистику.

### Вкладки
| Роль | Вкладки |
|---|---|
| Студент | Обзор (8 показателей + средний прогресс) · Статусы заявок (круг) · Заявки по месяцам · Прогресс практик · Дневник |
| Компания | Сводка · Статусы заявок (круг) · Заявки по практикам · Заявки по университетам · Заявки по месяцам |
| Университет | Сводка · Статусы заявок (круг, 3 группы) · Направления практик · Факультеты · Специальности · Заявки по статусам · Компании |

### API
| Метод и путь | Действие |
|---|---|
| `GET /api/stats/{student\|company\|university}/{метрика}?фильтры` | данные вкладки; роль в пути должна совпадать с ролью пользователя (иначе 403), неизвестная метрика → 404 |
| `…&format=csv` | та же статистика в CSV (UTF-8 BOM, `;`) |
| `GET /api/stats/facets?source=applications\|students\|practices&фильтры` | счётчики для панели «Фильтр»; `students` и `practices` — только университет |

Ответ бывает трёх видов: `kpi` (показатели), `doughnut` (сегменты с цветом), `bars` (строки `label/value`). Фильтры считаются тем же движком, что и списки (`listWhere` в `listEngine.ts`), поэтому права доступа те же: студент видит свои заявки, компания — заявки на свои практики, университет — своих студентов.

### Допущения этапа 6
- «В процессе» у студента = на рассмотрении + приглашён + на подписании. «Доля успешных решений» = одобренные ÷ (одобренные + отклонённые); пока решений нет, показывается «—».
- «Одобрено» = подписание, практика идёт, ожидает подтверждения, завершена.
- В сводке университета «Компаний» и «Предложений» считаются по всей платформе, а «Студентов с практикой» — доля студентов университета, у которых есть хотя бы одна не отклонённая заявка.
- Вкладка «Компании» университета: сколько его студентов дошло до подписания и дальше у каждой компании (один студент у компании считается один раз).
- «Заявки по месяцам» — последние 6 календарных месяцев (UTC) **по порядку времени**, а не по убыванию: иначе теряется смысл временного ряда. Остальные столбцы идут по убыванию.
- Вкладки «Факультеты» и «Специальности» считают студентов, «Направления практик» — предложения; для них панель «Фильтр» показывает поля, применимые именно к этим данным. При смене вкладки остаются только применимые фильтры.
- Агрегаты считаются на сервере по выборке до 50 000 заявок (как счётчики фильтров); для бо́льших объёмов понадобится `groupBy`/SQL.
- В `web/package.json` добавлены `chart.js`, `react-chartjs-2` и `@types/node` (последний чинит `npm run build`: `vite.config.ts` использует `process`).
- Проверено: `tsc` и `vite build` фронтенда проходят. Сервер я не смог проверить так же полно: `prisma generate` скачивает движок с `binaries.prisma.sh`, который в моей среде закрыт, поэтому типы Prisma не сгенерировались; новые серверные файлы дают только ошибки «нет типов Prisma», как и старые. Поведение API проверит `npm run smoke` (блок «этап 6»).

### Что нашли и исправили при написании тестов
- `?sort=constructor:asc` (и `__proto__`, `toString`): ключ сортировки проверялся через `cfg.sorts[key]`, а он находит свойства прототипа объекта — запрос падал с 500. Теперь `Object.hasOwn` (`listEngine.ts`). Тот же приём для `?source=` у `/api/stats/facets`.
- `?status=ЧТО-УГОДНО` в списках заявок и студентов уходил в Prisma как значение enum и давал 500. Неизвестные значения теперь отбрасываются, результат — пустой список.
- Лимит попыток входа вынесен в `AUTH_RATE_LIMIT` (по умолчанию 50 за 15 минут, как раньше), чтобы его можно было проверить тестом.

### Допущения этапа 7
- Тесты не проверяют Socket.IO-доставку и загрузку файлов (multer / sharp): их по-прежнему закрывает `npm run smoke`.
- Фронтенд тестами не покрыт.
- Проверки сортировки используют латинские названия и фамилии, чтобы порядок не зависел от collation базы.

- `smoke.mjs` оставлен: он гоняется по живому серверу и сидовым данным, а тесты — по изолированной базе.


## Этап 8: реестры ВУЗов и юрлиц РК, авторизация с проверкой, регистрация студентов

Задачи из заметки «на след. неделю»: (1) выгрузить все юрлица и ВУЗы РК и загрузить к себе; (2) авторизация с проверкой; (3) регистрация студентов.

### 1. Реестры в базе
| Таблица | Что внутри | Как наполняется |
|---|---|---|
| `RegistryUniversity` | ВУЗы РК: название, сокращение, город, БИН (если есть), источник | `npm run import:universities` — встроенный список из 88 ВУЗов (`server/data/universities-kz.json`) или ваш файл |
| `LegalEntity` | юрлица: БИН (первичный ключ), название, форма, сфера/ОКЭД, город, адрес, руководитель, дата регистрации, статус | `npm run import:entities -- файл.csv` |

```bash
# ВУЗы: встроенный список или официальная выгрузка
docker compose exec api npm run import:universities
docker compose exec api npm run import:universities -- /app/data/мой-реестр-вузов.csv

# Юрлица: положите файл в server/data/ (папка смонтирована в образ при сборке) и запустите
docker compose exec api npm run import:entities -- /app/data/legal-entities-sample.csv
```
- Форматы: CSV (разделитель `;`, `,` или Tab, BOM допустим), JSON (массив или `{items:[…]}`), JSONL. Заголовки распознаются по-русски, по-казахски и по-английски (`БИН`, `Наименование`, `Город`, `Статус`, `Сфера деятельности`, `ОКЭД`, `Адрес`, `Руководитель`, `Дата регистрации` …). Образец формата — `server/data/legal-entities-sample.csv`.
- Каждая строка проверяется: БИН — 12 цифр с верной контрольной суммой и признаком юрлица (5-я цифра 4–6), название обязательно. Плохие строки пропускаются и попадают в отчёт (первые 20 причин).
- Загрузка потоковая, пачками по 2000 (`INSERT … ON CONFLICT`), повторный запуск **обновляет** записи, дублей нет. Для миллионов строк работает минутами.
- `npm run db:indexes` создаёт trigram-индексы (`pg_trgm`) для быстрого поиска по подстроке названия; в Docker он запускается автоматически.
- Для каждого ВУЗа из реестра создаётся «карточка университета» (`accountStatus = UNCLAIMED`, войти нельзя), чтобы студент мог выбрать **любой** ВУЗ РК. Когда ВУЗ присоединяется к платформе: `npm run uni:account -- "КазНУ" rector@kaznu.kz` — карточка получает email и пароль, а уже зарегистрированные студенты остаются в ней.

**Важно: откуда брать данные.** Встроенный список ВУЗов составлен вручную и **не является официальным**: перед запуском в работу сверьте его с официальным реестром Министерства науки и высшего образования РК и загрузите официальную выгрузку той же командой (записи сопоставляются по БИН или по названию+городу). Реестр юрлиц с реальными БИН в проект не входит: сведения публикует Бюро национальной статистики (stat.gov.kz) и портал открытых данных data.egov.kz — выгрузите оттуда файл и загрузите командой выше. В `seed` лежат только **демонстрационные** юрлица с тестовыми БИН (`source = DEMO`).

### 2. Авторизация с проверкой
- **Подтверждение email.** После регистрации аккаунт в статусе `PENDING_VERIFICATION`, вход не выдаётся. На почту уходит 6-значный код (15 минут, не более 5 попыток, повторная отправка не чаще раза в минуту; в базе только HMAC-хэш кода). После ввода кода — аккаунт `ACTIVE` и сразу выдаются cookie. Если пользователь пытается войти, не подтвердив email (пароль верный), он получает `403 EMAIL_NOT_VERIFIED`, новый код и переходит на страницу ввода кода.
- **Проверка компании по БИН.** Компания регистрируется только по БИН: он должен пройти контрольную сумму, быть в реестре юрлиц, быть действующим и ещё не занятым. Название берётся **из реестра** (нельзя вписать чужое), у компании ставится `verified = true`, название в профиле не редактируется. Форма проверяет БИН «на лету» и показывает найденную организацию.
- **Проверка ВУЗа студента.** ВУЗ выбирается только из реестра (поиск по названию/сокращению прямо в форме).
- Карточки ВУЗов без владельца войти не могут. Неподтверждённая регистрация не блокирует email и БИН: её можно перезаписать.
- **Почта.** Без `SMTP_HOST` письма печатаются в консоль API, а в режиме разработки код показывается на странице подтверждения. Для настоящей отправки заполните `SMTP_*` в `.env`.

### 3. Регистрация студентов
Поля: имя, фамилия, ВУЗ (из реестра), специальность, факультет, курс, город, навыки, email, пароль → код из письма → вход в кабинет.

### 4. Реестры в интерфейсе
Страница `/registry` («Реестры РК» в меню): сводные счётчики, вкладка «ВУЗы РК» (открыта без входа) и «Юридические лица» (после входа): поиск, фильтры по городу и статусу, серверная пагинация.

### Допущения и ограничения этапа 8
- **Код в этой среде не запускался**: нет сети, `npm install` и `prisma generate` недоступны. Проверен только синтаксис TypeScript и логика БИН/парсеров отдельным прогоном. Первый запуск `npm test` и `npm run seed` у вас — главный тест. Схема изменилась, поэтому на существующей базе выполните `npx prisma db push` (в Docker — автоматически) и заново `npm run seed`.
- Совпадение БИН + подтверждённый email **не доказывают**, что человек представляет эту компанию. Для строгой проверки нужны ручное одобрение администратором, проверка корпоративного домена почты или подпись ЭЦП через NCALayer — это следующий шаг.
- Не вводятся ИИН и ИП/КХ (у них ИИН): только юрлица с БИН.
- Число записей в списке юрлиц считается `COUNT(*)`: на десятках миллионов строк без фильтра это может занять заметное время.
- В `seed` университеты ЕНУ и «МНУ» (демо) забирают свои карточки из реестра; остальные ВУЗы — `UNCLAIMED`.
- Старый `smoke.mjs` регистрации не затрагивает и должен работать как раньше.
